| Area | Unsafe or unresolved cases | Controls |

| SENT-002 | Named helpers, multiple hops, returned input, keyword/destructured binding, recursion and imported-helper limitations | Direct execution positive; constant arguments/returns, overwrite, unused helper definitions |
| SENT-003 | Unrelated validation, discarded parsed output, partial fields, ignored result, late/conditional checks, replacement, permissive framework input | Consumed parsed output, non-transforming JSON Schema/Ajv checks, custom guards, early return, type/bounds/allowlist checks, recognizable framework schema |

| SENT-004 | Raw content, discarded sanitizer output, unrelated content, overwrite, raw reintroduction, branch bypass | Configured sanitizer result, both branches protected |

The unrelated-authentication comparison deliberately compares the trusted value
with itself: it succeeds without authenticating the incoming credential. The
unrelated-manifest check deliberately verifies the known original bytes: it can
succeed while different consumed bytes remain unchecked. Neither reproduction
depends on a comparison that accidentally rejects every request.

Signature controls contain locally generated public keys and valid signatures
for the original `b"{}"` manifest. A host-side check of these fixed public
vectors confirmed all three signatures and rejected altered manifest bytes.
Private keys were not retained. Python `cryptography` verification raises on
failure; ignoring its successful `None` return is valid. Node's synchronous
boolean verification result must be enforced.

The configured sanitizer is deliberately an identity function. This tests the
user's explicit configuration trust decision and propagation of its result; it
does not claim that the function prevents prompt injection.

Some controls expose false alarms or newly requested recognition, rather than
missed vulnerabilities. A safe route yielding no finding does not establish
route recognition by itself; its unprotected counterpart is also tested.
These are development regression cases, not held-out precision/recall or
ecosystem coverage measurements. Code coverage is a separate engineering metric.

## Checkpoint 2 — same-file execution flows

The user's `continue` approved checkpoint 2. The implementation extends
`SENT-002` using the existing Python AST and TypeScript source recognizer, with
shared parameter-dependency summaries and an iterative helper traversal. Semgrep
remains installed, pinned, and invoked through the existing scan pipeline.

Supported flows include top-level named helper chains, explicit positional and
Python keyword arguments, simple TypeScript object-field destructuring,
assignments, returned values, and ordinary conditional branches. Constant
arguments and constant helper returns do not become input-derived execution
candidates. Defaults are not evaluated: every argument must be explicitly bound.
Python decorators/generators and unawaited asynchronous helpers remain unresolved.

Unknown calls, ambiguous bindings, spreads, dynamic aliases, methods, nested
functions, recursion, and unsupported control or mutation paths use the existing
report-warning shape with code `static_flow_unresolved`. Unknown calls alone do
not establish an execution sink. Unsupported effects prevent the new analysis
from certifying a constant return. This is bounded recognition, not a full
Python/TypeScript interpreter or a claim of complete data-flow coverage.

New helper findings identify the tool's helper call and describe the known sink
and its source line. Separate calls remain separate findings, including calls
on one TypeScript line; sinks reached through the same call are combined.
Existing direct findings retain their locations and identity construction.
Inline suppression applies at the new primary call site.

The existing review context builder is reused without changing its windows or
request construction. Flows extending beyond those windows add
`static_review_context_incomplete`, including helper return flows feeding direct
sinks. This warning does not enlarge model access or initiate a model call.

There is no helper-depth setting or fixed hop limit. Both recognizers were
checked with 1,100-helper chains, independently of Semgrep, and the shared

## Checkpoint 3 — safety exemptions

Validation exemptions now follow the consumed input through assignments and
ordinary conditional paths. Parsed Pydantic/Zod results, enforced JSON Schema/Ajv
checks, primitive framework schemas, and custom field guards have paired
controls. Unrelated checks, discarded results, unchecked fields, late checks,
and replacement after validation do not protect the consumed value.

Authentication exemptions require recognized framework imports, applicable
route or middleware registration, and enforcement of a request-credential check
against a trusted literal or environment anchor. Controls cover FastAPI,
Starlette authentication plus permission enforcement, Express, and Hono.
Middleware installation or an authentication-related name alone is insufficient.

Manifest exemptions require enforced SHA-256 comparison or supported native
signature verification over the consumed bytes. Controls cover literal anchors
and validated sidecar references, including bound public-key/signature files.
Python cryptography and Node verification recognize Ed25519, RSA-PSS-SHA256,
and ECDSA-SHA256. Public-key data is parsed with the existing installed dependency;
no target code runs and no dependency was added.

Configured sanitizer trust follows its result. Discarding that result,
overwriting it, or reintroducing raw content retains the finding. Configuration
is an explicit trust decision, not evidence of prompt-injection resistance.

These are bounded source recognizers. Ordinary `if`/`else`, rejecting exits,
and simple assignments are covered; this is not arbitrary control-flow,
framework, or language coverage. Finding shapes, rule IDs, CLI contracts, and
review-context limits are unchanged.
